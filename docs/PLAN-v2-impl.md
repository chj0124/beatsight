## 1. 范围（明确做什么、不做什么）

**做（档位①′ + 块结构）**：

- 曲式库（多条曲式，冷键持久化）+ 段落名字
- 段 = **有序的若干块**（`blocks`），每块 = 一个预设引用 + 整数遍数
  → (a) 型段 = 1 块；**(b) 型段 = 2 块**（这正是 D8=混合 所要求的）
- 播放范围 `[from, to]` + 范围循环
- **小节边界跳段**（播放中跳到任意段）
- 同屏仍是 4 行（**不做**段落自适应行数）

**不做（写在这里是为了防止实现时顺手扩）**：

| 不做 | 为什么 |
|---|---|
| 段落自适应行数（档位②） | (a) 型段落的第 5–8 小节与第 1–4 逐音符相同，多画 4 行无新信息；窄屏还会被挤爆。替代：段落进度条 |
| 变拍号 | `S.sig` 语义牵连整个 UI，是档位③′ 唯一剩下的昂贵部分 |
| 拖拽排序 / 每段单独 BPM | 上移下移足够；每段调速会与变速训练器、练习量三者交叠 |
| 播放中任意**小节**跳转 | 需要相位换算；段级跳转已够用 |
| 曲式的导入导出 | 冷键已存本机；等真有备份需求再加（照 `serializeLog` 的范式） |

## 2. 数据模型

### 2.1 冷键 `beatsight.arranges`（曲式库）

```js
{ v: 1, arranges: [
  { id: "a1758…", name: "某首歌",
    sections: [
      { name: "前奏", blocks: [ { ref: {type:"builtin", idx:0}, repeats: 1 } ] },
      { name: "主歌", blocks: [ { ref: {type:"custom",  id:"c…"}, repeats: 2 } ] },        // (a) 型：1 块 × 2 遍 = 8 小节
      { name: "副歌", blocks: [ { ref: {type:"builtin", idx:4}, repeats: 1 },              // (b) 型：2 块 = 8 小节
                                { ref: {type:"builtin", idx:2}, repeats: 1 } ] },
      { name: "间奏", blocks: [ { ref: {type:"builtin", idx:0}, repeats: 1 } ] },
      { name: "主歌", blocks: [ { ref: {type:"custom",  id:"c…"}, repeats: 2 } ] },        // 同一预设复用
      { name: "副歌", blocks: [ { ref: {type:"builtin", idx:4}, repeats: 1 },
                                { ref: {type:"builtin", idx:2}, repeats: 1 } ] },
    ] }
] }
```

**设计要点**：

- **所有段统一用 `blocks` 数组**，(a) 型段只是"1 个块"。不做"有的段用 `repeats`、有的段用 `blocks`"
  的双形状——双形状意味着每条读写路径都要判两次，而两种形状的差别只有一层数组
- `ref` 复用 `S.sel` 的形状（`{type:"builtin", idx}` / `{type:"custom", id}`）→
  解析走**同一个** `resolveRef()`（见 §4.1），不会出现"曲式里的预设"与"当前预设"两套边界
- 段名可重复（主歌出现两次是正常的）；`id` 是唯一的
- 段内小节数 = `Σ(block.repeats) × 4`，**由数据派生**，不存字段（存了就会与 blocks 不同步）

### 2.2 热键新增字段

```js
S.playMode  = "preset" | "arrange"          // 二选一：播当前预设，还是播曲式
S.arrangeSel = { id, from, to, loop }        // 当前曲式 + 播放范围（段 index，含端点）
```

**为什么进热键**：用户会长期"只练副歌"（`from = to = 副歌`、`loop = true`），
每次打开都要重设会很烦。`from/to/loop` 是"我这次练习的意图"，与 `S.limit` 同类，属热键。

**为什么用独立的 `playMode` 而不是扩 `S.sel` 的 type**：`S.sel` 会被 `selectedPreset()` /
`curPattern()` / `Presets.buildPresetList` / 编辑器等一堆地方读。塞一个 `"arrange"` 进去，
每个读取点都要判一次"这是不是曲式"，而其中大多数点对曲式没有意义——
污染面比新加一个字段大得多。

### 2.3 校验（`Store` 内，类比 `validatePreset`）

| 检查 | 拒绝理由（弹窗文案要给具体位置） |
|---|---|
| `name` 非空、≤ 40 字 | 「曲式名不能为空」 |
| `sections` 1–24 段 | 「曲式至少要有 1 段 / 最多 24 段」 |
| 每段 `blocks` 非空、≤ 8 块 | 「第 N 段没有任何内容」 |
| `repeats` 为整数 1–16 | 「第 N 段第 M 块的重复遍数必须是 1–16 的整数」 |
| 每个 `ref` 能解析到**存在的**预设 | 「第 N 段第 M 块引用的节奏型不存在（可能已删除）」 |
| **所有块的 meter 相同** | 「第 N 段的拍号与第 1 段不一致——v2 要求整首同拍号」 |
| 总小节数 ≤ 256 | 「曲式太长（超过 256 小节）」 |

**加载时**（从冷键读）：逐条校验，**坏条目丢弃并记 warn**（与 `customs` 的隔离策略不同——
曲式丢了只是要重编，不值得占用隔离区与弹窗名额；口径参照 `beatsight.log`）。

**引用失效的处理**：加载时不因引用失效而丢弃整条曲式，而是**标记该块为失效**；
播放到失效块时**跳过它**并提示一次（参照 `curPattern()` 的 `basicPattern` 回退语义）。

## 3. 会话状态（共享状态区新增）

```js
let arrSec = 0, arrBar = 0;    // 当前段 index、段内小节 index（0 基）
```

**不持久化**：每次 `Controls.start()` 从播放范围起点重置，与 `limitBars` / `schedBar` 同类。

**与 `schedBar` 的分工**（关键，别混）：

| 变量 | 含义 | 范围 |
|---|---|---|
| `schedBar` | **当前那个节奏型内部**的 4 小节循环游标 | 0–3，**不改** |
| `arrBar` | **段内**已走过的小节数 | 0 – (段长−1) |
| `arrSec` | 当前第几段 | 0 – (段数−1) |

`arrBar` 的用途只有两个：判断"该不该换块/换段"、以及显示段进度。
**可视化仍由 `schedBar` 驱动**（所以 `buildViz` / `paintFrameBody` 一行不改）。

## 4. 核心机制

### 4.1 `resolveRef(ref)` —— 抽出一处

现在"把 `{type,idx}` 或 `{type,id}` 变成节奏型对象"的逻辑在 `selectedPreset()` 里，
但它是绑着 `S.sel` 的。曲式需要解析**任意** ref。

**改动**：抽出 `resolveRef(ref) → pattern | null`，`selectedPreset()` 改为 `resolveRef(S.sel)`。
纯重构，行为零变化（**单独提交**，跑全量断言确认）。

### 4.2 `arrNextBar(a)` —— 「沿节目单步进」**只有这一份**

```js
/* 沿节目单前进一小节。a = 曲式对象。
   返回 { sec, bar, blockIdx, ref, blockChanged, sectionChanged } 或 null
   （null = 已到播放范围末尾且不循环 → 调用方应停止播放）。

   ★ scheduler（实际排程）与 predictNext（弹跳球预测）**必须都走这一个函数**。
   两边各写一份步进逻辑的话，一旦不一致就会在段/块边界分叉——
   而分叉会同时打坏弹跳球、播放头、和待命球的交接，且极难复现。
   （阶段一探针 §5 把这个列为 ①′ 里唯一容易埋雷的地方） */
```

派生出的两个辅助（都基于同一份数据，不各自算）：

- `secBars(a, sec)` → 该段总小节数 = `Σ(block.repeats) × 4`
- `blockAt(a, sec, bar)` → `{blockIdx, localBar}`（块起始小节是各块 `repeats × 4` 的累加）

### 4.3 把曲式切换接入**现有的挂起路径**（不新写一条）

现在 `Presets` 里有一条已验证的挂起机制：

```
refreshAfterPatternChange()  → 试 resyncToNow()；失败则 pendingPattern = true
scheduler 小节边界 → consumePending(schedBar) → {applied:true, resetBar}
                   → schedBar = resetBar; loopStart = nextNoteTime − schedBar × S.sig × spb()
                   → Viz.resetTracking(); return
```

**曲式的块/段切换走同一条路**，只把"待应用的东西"从"`curPattern()`"泛化为"一个 `pendingRef`"：

- 预设选择 → `pendingRef = S.sel`
- 曲式块切换 → `pendingRef = 该块的 ref`

`consumePending` 内部把 `applyPatternChange()` 的取型来源改成 `resolveRef(pendingRef)`。
**曲式切换时 `resetBar` 恒为 0**（新块从它自己的第 0 小节开始）。

**为什么不新写一条"曲式切换"路径**：这条路径已经处理好了
"scheduler 中途退出 + `loopStart` 重映射 + `resetTracking` + 与变速训练器的次序"一整套，
另写一条 = 把那些坑再踩一遍。这与阶段一探针 §3.1 的选择一致。

### 4.4 跳段

**跳段不立即生效，在下一个**小节**边界生效**（最多等 2.5 秒）。实现：
把 `arrSec/arrBar` 置为目标段与 0，并设 `pendingRef = 目标段第 0 块的 ref`。
下一次小节边界由 §4.3 的路径统一施加。**不需要任何相位换算**（这是阶段一探针
把"跳段"从档位③ 下移到①′ 的依据）。

**顺带（便宜且有用）**：因为跳段只依赖"下一个小节边界"，播放中也可以**跳块**
（跳到段内第 k 块）——同一套逻辑，不加成本。

### 4.5 范围与末尾

`arrNextBar` 走完 `to` 段的最后一小节时：

- `loop = true` → 回到 `from` 段第 0 小节（**范围循环**；`from === to` 即"单段循环"）
- `loop = false` → 返回 `null`，`scheduler` 在此调用 `Controls.stop()`（复用现有停止路径）

### 4.6 与既有三条横向机制的关系

| 机制 | 关系 |
|---|---|
| **练习量 `limitBars`** | **不改**。整首累计（D6 已定）。与范围循环天然配合：设"只练副歌 + 范围循环 + 16 小节"= 副歌练 2 遍 |
| **变速训练器 `Trainer.onBarBoundary`** | 在小节边界调用。**次序**：先训练器（可能返回 true 停止），再曲式推进，再挂起消费。写进代码注释 + 断言（R3） |
| **静音拍 `S.mute`** | **不改**，保持"全局每 4 小节静音第 4 小节"（D5 已定：按全局）。曲式模式下允许直接关掉 |

## 5. UI

### 5.1 编排 overlay `#arrangeOverlay`

与 `#editor` / `#statsOverlay` / `#earOverlay` 同一套（全屏 overlay + `Modal.refreshInert()` +
`Escape` 关闭 + 键盘路由加 `Ear` 式的一支）。

布局：

```
返回练习 | 曲式编排                                    [新建] [保存]
─────────────────────────────────────────────────────────────
曲式列表（左）          段落结构（右）
  某首歌        ←选中    曲式名 [____________]
  另一首                 ┌ 段 1  前奏   [🎵八分摇滚 ×1]        ↑ ↓ ✕
                         ├ 段 2  主歌   [🎵民谣扫弦 ×2]        ↑ ↓ ✕
                         ├ 段 3  副歌   [🎵切分 ×1] [🎵Funk ×1] ↑ ↓ ✕
                         └ …
                         [+ 加一段]  [+ 给本段加一块]
─────────────────────────────────────────────────────────────
播放范围：从 [段▾] 到 [段▾]   ☑ 范围循环      [▶ 从头播] [▶ 播选中范围]
```

- 段名用 `contenteditable`？不用——用 `<input>`（与 `presetNameInput` 一致，测试也好断言）
- 块里的"改预设"：点块 → 下方出现预设选择（复用 `Presets` 的列表渲染，不重写一份）
- 上移/下移/删除：复用现有 pill 按钮范式（与编辑器按钮区同构）

### 5.2 主界面（曲式模式下的显示）

- `patternName` 位置改显「**曲式名 · 当前段名**」，`patternMeta` 加「第 k/N 段 · 全曲第 m/M 小节」
- 段进度：一条细进度条或文字（**不做**多行可视化）
- 跳段控件：`[◀ 上段] [段名▾] [下段 ▶]`（跳段在小节边界生效，按钮上给"下一个音符切换"的提示）
- 预设库区域：曲式模式下预设列表**变暗并标注"选择预设会退出曲式模式"**——
  比静默切走好，也不做"点预设 = 换当前段的型"那种聪明交互（那是 v2.1 的事）

### 5.3 入口

**放在预设卡片里**，作为与预设库并列的一个区块（「曲式」区，列出曲式名 + 一个「编排」按钮）。
理由：曲式与预设是**同一层概念**（都是"播放什么"），放一起用户不用找；
放在训练模式区会让人以为它是个训练功能。

## 7. 反向验证变异清单（预先列出，实现时直接用）

| # | 变异（把逻辑退回成错的样子） | 期望变红的断言 |

| V7 | 待命球的"下一行"仍用 `(bar+1) % 4` | 段末待命球断言 |
| V8 | 跳段立即生效（不等小节边界） | "跳段在下一个小节边界生效"断言 |

| V11 | 引用失效时丢弃整条曲式（而不是标记跳过） | "只跳过失效块，其余照常"断言 |
| V12 | 静音拍判定改成"每段最后一小节" | 静音拍仍为全局每 4 小节断言 |

**纪律提醒**（`tests/README.md` 已写）：变异后必须出现**具名断言失败**；
若整套以 TypeError 崩溃，先修断言的脆弱性再重跑。写断言时凡取下标/`find()` 结果，
一律兜空对象。

**S1 为什么单独提交**：它是唯一"应该零行为变化"的一步。混进功能改动后，
一旦断言变红就分不清是重构错了还是功能错了——这一步单独提交并确认 936 条全过，
后面每一步的失败都能定位到当步。

**S4 是本方案风险最高的一步**（动 `predictNext` 与待命球）。建议在 S4 里
**先把 T21 的段边界相位扩出来并跑通**，再改 `predictNext`——先有网，再走钢丝。

## 9. 风险（在探针 §6 之上新增）

| # | 风险 | 缓解 |
|---|---|---|
| R8 | **`arrBar` 与 `schedBar` 混用**（两者都叫"bar"） | 命名上刻意区分（`arrSec/arrBar` vs `schedBar`）；§3 的表格写进代码注释；T53 专测"块边界 `schedBar` 归零" |
| R9 | 段内两个块**用的是同一个预设**（(b) 型段恰由同一型构成） | 此时**不要**切 `pendingRef`（无型可换）——只在 ref 真的变了才挂起，否则会白白重置 `schedBar` 造成视觉跳一下。列为 V2 的一个变体 |
| R10 | 曲式模式下用户点预设造成状态混淆 | §5.2 明示"会退出曲式模式"；不做"改当前段"的聪明交互 |
| R11 | 段数/块数上限设得太松，UI 列表长到不可用 | 24 段 / 8 块 / 256 小节的硬上限 + 列表内滚动 |
| R12 | 曲式很长时 `arrNextBar` 的循环次数 | 它每次只前进一小节（不在循环里搜），无性能问题；但要避免"找下一个非空块"这类跨段搜索写成嵌套循环 |
