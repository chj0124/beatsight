## 0.5 阶段一补记：D7 已答 = 真实歌曲结构（本节的结论覆盖前文相应处）

**你的回答：练的是「前奏 4 → 主歌 8 → 副歌 8 → 间奏 → 主歌 → 副歌」这种真实歌曲结构。**
这个答案确认了三件事，也**推翻/削弱了前文两处结论**，并暴露一个**新的硬约束**。

### 确认的三件事

1. **结构是「序列」而不是「集合」**：主歌出现两次 → `sections` 必须是**有序数组、允许重复项**。
   §3.1 那个 `sections: [{ref, repeats}]` 形状本来就支持（数组可以有重复项），不用改。
2. **段长是 4 的倍数**：前奏 4、主歌 8、副歌 8、间奏 4 —— 音乐本来就是 4 小节乐句为单位。
   所以 §6 的 R4（"段长必须 = 4 的倍数"）是**成立的约束**，可以把 `repeats` 做成整数遍数。
3. **同一个节奏型会出现在多个段**（前奏与主歌很可能用同一个扫弦型）→ 段落必须能**引用同一个预设**，
   而不是"一段一个专属节奏型"。`ref` 复用 `S.sel` 形状同样满足。

### ★ 新暴露的硬约束：「主歌 8 小节」有两种含义，而现有数据模型只能表达其中一种

盘点时核验出一件事（前文没写）：

> **预设上限就是 4 小节**（`validatePreset` 要求 `bars.length === LOOP_BARS`），
> **但这 4 小节可以各不相同**——编辑器本来就支持逐小节编辑（`editBar` 选中哪一小节，
> 后续插入就落在哪一小节；`copyBarBtn` 是"把当前小节复制到全部"，说明默认**不**复制）。
> 只是**内置的 12 个预设恰好都用了 `rep4()`**，所以看起来"4 小节永远一样"。

于是「主歌 8 小节」有两种完全不同的含义：

| | 含义 | 现有模型能表达吗 | 代价 |
|---|---|---|---|
| **(a)** | 同一个 4 小节伴奏型**放 2 遍**（吉他弹唱最常见：主歌就是那个扫弦型一直弹） | ✅ 能 —— `sections: [{ref: 主歌型, repeats: 2}]` | 档位① 直接覆盖 |
| **(b)** | **两个不同的 4 小节乐句**（第 5–8 小节与第 1–4 不同，如 AA'BA'） | ❌ **不能** —— 没有任何办法把"8 个不同小节"塞进一个 4 小节的预设 | 需要"段 = 有序的若干块"，各块引用不同预设（+0.5 批次） |

**(b) 的解法**：把"段"从"一个预设 × N 遍"升级为"**有序的若干块**"：

```js
{ name: "主歌", blocks: [ {ref: 前4型, repeats: 1}, {ref: 后4型, repeats: 1} ] }
```

这比"段 = 一个预设 × N 遍"只多一层数组，代价不大，但它让"段落名字"与"块"的层级关系变清楚
（用户看到的是"主歌"，内部是两个块）。

### 被削弱的结论一：档位②（段落自适应行数）对 (a) 型段落基本没有价值

主歌 8 = 同一个 4 小节 × 2 遍时，**第 5–8 小节与第 1–4 小节逐音符完全相同**。
多画 4 行不提供任何新信息，反而把行高压缩、把窄屏挤爆（§3.2 已算过：8 行 × 86px = 688px）。

**所以：如果是 (a) 型，② 可以直接不做**；如果是 (b) 型，② 的价值也有限——
因为"段内的两个 4 小节组"用 ① 的块结构就能各自画成 4 行（块边界即行边界）。

**结论：② 从"推荐的第二步"降级为"可选，且很可能不需要"。**
替代方案更便宜：曲式模式下显示一个**段落进度条**（现在在第几段 / 段内第几小节 / 全曲进度），
而不是把所有小节画出来。

### 被修订的结论二：D2 的答案倾向变了，而"跳段"比原先估的便宜

真实歌曲 40 小节 ≈ 96BPM 下 100 秒。**你不会每次都从间奏开始练**——所以：

- "只播选中段 / 范围循环"从**可选**变成**刚需**
- 原先我估"任意跳段属于档位③（+2–3 批次）"——**这个估计过重了**。跳段其实可以复用现有机制：
  - **播放范围 + 范围循环**：节目单游标加两个边界字段即可，**很便宜**
  - **播放中跳段**：等价于"换节奏型 + 把循环游标重置到 0"，而这正是
    `Presets.consumePending` 返回 `{applied, resetBar}` 已经在做的事
    （`scheduler` 拿到 `resetBar` 后会重映射 `loopStart`）。
    所以跳段**在下一个**小节**边界生效**（最多等 2.5 秒），不需要任何相位换算
- 于是档位③ 真正昂贵的部分**只剩下「变拍号」**（`S.sig` 语义）**与复杂编排 UI**

### 修订后的档位表

| | 档位①′ 播放层面串联（含名字/范围/跳段） | 档位③′ 变拍号 + 拖拽编排 UI |
|---|---|---|
| 内容 | 节目单 + 段落名字 + 播放范围/范围循环 + 小节边界跳段 + （需要则）块结构 | ①′+ `S.sig` 变成"当前段拍号" + 独立编排编辑器 |
| 代价 | **2 – 2.5 批次**（比原估 +0.5，因多了名字/范围/跳段/块） | 再 +1.5 – 2（比原估 −1，因跳段已下移到①′） |
| 动音频核心吗 | **不动时间轴不变量** | **动**（拍号语义） |

**修订后的建议：做档位①′。** 它已经能完整支撑"编出一首真实歌曲的结构 → 从头练到尾 →
单练某一段 → 跳段重来"这一整套练习流程。②′ 很可能不需要；③′ 只剩变拍号与拖拽 UI，
可以等你真的遇到"一首歌中途变拍号"再考虑。

## 1. 为什么不能"顺手加上"

现在的音频核心是：**一个节奏型 + 一个 4 小节循环 + 一个时间轴锚点**。这三件事是互相咬合的：

```
loopStart ────┬── 小节 0 ── 小节 1 ── 小节 2 ── 小节 3 ──┐
              └──────────────── 回到小节 0 ──────────────┘
              nextNoteTime == loopStart + tick × spb/TPB   ← 核心不变量
              appliedPat = 当前那个节奏型（唯一）            ← 核心假设
```

曲式要的是：`[前奏 ×4] → [主歌 ×8] → [副歌 ×8]`。这等于要求**"循环什么"本身也要有时间结构**——
于是"4 小节"从"世界的尺寸"变成了"段落的属性"，而**时间轴锚点、发声快照、渲染行数、视觉追踪**
四样东西都建立在"世界的尺寸是 4"之上。

不是不能改，而是**改动会沿这四条线扩散**——所以先盘清楚有哪几条线。

## 2. 事实盘点：严格 4 小节循环 = 18 条假设

`LOOP_BARS = 4` 是唯一常量，但它的**语义**散落在 18 处。按"曲式化后要不要动它"分三档标注：

详见 §0.5 —— 它是 D7 的答案（真实歌曲结构）直接带出来的。

**三个最值钱的行是 4、5、6**，它们不是"改个数字"，而是**语义要重新定义**：

- **#4 / #5**：`predictNext` 和待命球都只看得到当前这个 4 小节循环。曲式里，**段落最后一小节**
  需要"看到"下一段的第一个音——否则球在段落边界会停住、待命球没有目标。
  这不是把 `LOOP_BARS` 换成"当前段长度"就行：它要求预测能**跨段**。
- **#6**：「静音拍 · 每 4 小节静音第 4 小节」在曲式里是什么？按段静音（每段最后一小节）？
  还是保持"全局每 4 小节"？**这是一个你现在还没想过、但必须在动工前定下来的产品问题。**

## 3. 三个档位详述

### 3.1 档位① 播放层面串联（最小）

**数据模型**（新增冷键 `beatsight.arrange`）：

```js
{ name: "xxx", v: 1,
  sections: [
    { ref: { type: "builtin", idx: 0 }, repeats: 4 },   // 前奏，放 4 遍（= 16 小节）
    { ref: { type: "custom",  id: "c1758..." }, repeats: 8 },
  ] }
```

`ref` 的形状**刻意复用现有 `S.sel`**（`{type:"builtin", idx}` / `{type:"custom", id}`）——
这样"从曲式里挑一段"和"直接选预设"是同一套解析逻辑（`selectedPreset()`），不必再写一份，
也不会出现"曲式里的段"与"当前预设"两套边界不一致。

**播放**：新增两个会话游标 `arrIdx`（第几段）+ `arrBar`（段内第几小节）。
小节边界处：`arrBar++`；放满 `sections[arrIdx].repeats × LOOP_BARS` 后 `arrIdx++`，
并把下一段交给 `applyPatternChange`。

**段落切换用「小节边界挂起」**（`Presets.consumePending` 的泛化）——
不用 `resyncToNow`（相位就地接续）。理由：
- 段落切换**天然发生在小节边界**（段长是 4 的整数倍），不需要"中途插进去"
- `resyncToNow` 是给"用户在播放中随手点了个别的节奏型，希望立刻生效"用的；
  它的相位换算在小节末会顺延到下一小节（已有 `j < 0` 分支），**语义上就是"尽量接近边界"**
- 挂起路径已经处理好了"scheduler 中途退出 + `loopStart` 重映射 + `resetTracking`"这一整套
  （`consumePending` 返回 `{applied:true, resetBar}`），复用它比自己再写一条便宜得多

**可视化**：仍是 4 行——就是当前那一段的 4 小节。`buildViz` / `paintFrameBody` 一行不用改。

**必须处理的边界**：`predictNext` 与待命球在**段末**要能看下一段（#4 / #5）。
做法：把"向前找下一小节"的步进从 `(schedBar + k) % LOOP_BARS` 改成
"沿节目单步进"（段内 +1，段末跳到下一段第 0 小节）。这是一个**局部改动**，
但它必须与 `scheduler` 的游标推进用**同一个函数**——否则预测与实际排程会在段末分叉，
而那正是 T22/T30 一直在守的东西。

**拍号**：档位① 要求**整首同拍号**。相邻两段拍号不同的曲式在保存时直接拒绝并提示原因。
（现有 `consumePending` 的 `sigChgPending` 逻辑是"拍号变则等到 `schedBar === 0`"，
段落边界与循环起点不重合时这条规则需要重新定义——那是档位③ 的活。）

**编排 UI（简版）**：训练模式区或预设区新增一个入口 → overlay 列表：
「选预设（复用预设库）+ 填重复遍数 + 上移/下移 + 删除」+ 一个「从头播 / 只播选中的段」。

**代价**：1.5 – 2 批次。改动集中在 `Audio.scheduler`（游标）、`Presets`（挂起泛化）、
一个新冷键 + 一个简版 UI。**不碰时间轴不变量**（#2 保持原样，只是 `appliedPat` 会在段边界换人）。

**受影响测试**：T12（小节边界无缝切换）、T15（切拍号）、T20（点下即生效）、
T21（9×9 组合 × 3 相位全量扫描）、T48（练习量按小节）。
这些守的都是"切换"这件事，档位① 动的是同一处逻辑 → **必须逐条重跑并确认不变量仍成立**。

### 3.2 档位② 段落自适应可视化

在① 之上让"同屏小节数"随段落变：一段 8 小节就画 8 行。

**改动**：`Viz.buildViz`（行数由当前段长决定）、`Viz.paintFrameBody`（行号映射、进度换算）、
`vizTitle` 文案、以及**桩的几何模型**——
测试沙箱里 `_rowTop = 58 + i × 86` 是"按创建序分层"的硬编码假设，行数变化要让它跟着支持
（否则弹跳球的位置断言全是假的，而假绿比没测更糟）。

**风险点**：行数多了以后，在 390px 窄屏上 8 行 × 86px = 688px 高，加上顶部 58px 空域，
一屏放不下。**这不是渲染 bug，是设计取舍**——要么滚动、要么缩小行高、要么按屏高自适应。

**代价**：+1 – 1.5 批次。**不动音频**，纯渲染层。

> **⚠️ D7 已答后本档位已降级为"很可能不需要"**（见 §0.5）：真实歌曲的"主歌 8 小节"若属 (a) 型
> （同一个 4 小节伴奏型 × 2 遍），第 5–8 小节与第 1–4 小节**逐音符完全相同**，
> 多画 4 行不提供任何新信息，反而把窄屏挤爆（8 行 × 86px = 688px）。
> 更便宜的替代：曲式模式下显示一个**段落进度条**（现在在第几段 / 段内第几小节 / 全曲进度）。

### 3.3 档位③ 完整曲式编辑器

在② 之上再加：

- **独立的全屏编排 UI**：拖拽排序、段落命名、每段重复遍数 + 每段 BPM
- **变拍号**：`S.sig` 从"全局唯一"变成"当前段的拍号"。这一条牵连很广：
  拍号 pill 的选中态、`updateMeta`、`meterName`、`Controls.setSig` 的语义、
  以及 `consumePending` 里"拍号变则等到循环起点"那条规则（段落边界 ≠ 循环起点）
- **任意跳段**（不只顺序推进）：这是对 `resyncToNow` 的泛化——
  要能在"主歌第 3 小节"直接跳到"副歌第 1 小节"，且不排到过去、不跳针

**代价**：再 +2 – 3 批次。**这是唯一会动时间轴不变量的档位**，也是返工风险最集中的档位。

## 5. 分阶段落地路径（推荐）

> **D7 已答后的修订版**（见 §0.5）：② 降级为可选且很可能不需要；跳段下移进 ①′。

```
①′ 播放层面串联（节目单 + 段落名字 + 播放范围/范围循环 + 小节边界跳段）
   → 可独立发布（v2.0.0）  覆盖"编结构 → 通练 → 单练某段 → 跳段重来"整条练习流程
   │
   ├─ 块结构（段 = 有序的若干块）      → 仅在 D8 答 (b) 时需要（+0.5 批次，纯加法）
   ├─ 段落进度条（替代"自适应行数"）   → 便宜，可选
   └─ 变拍号 + 拖拽编排 UI            → 再 +1.5–2，等你真遇到变拍号的曲子再考虑
```

**为什么按这个顺序**：

1. ①′ 完成时就已经能"把一首真实歌曲编出来并从头练到尾、还能单练副歌"——这就是你要的东西
2. 剩下的三项都是**纯加法**（块结构加一层数组；进度条是新的只读展示；变拍号是独立维度），
   任何一项都可以在实际用了一阵子后再决定
3. **没有任何一步需要动时间轴不变量**（变拍号那一步才需要，而它已排到最后）
4. 每一步都能单独发布 → 效果不好就停下，不会"箭在弦上"

**关键做法**（不变）：①′ 里那个"沿节目单步进"的函数必须**只有一份**，被 `scheduler`（实际排程）与
`predictNext`（预测）共用。这是 ①′ 里唯一容易埋雷的地方——预测与实际分叉会同时打坏
弹跳球、播放头、和待机球的交接。

**新增的第二个关键做法**：**跳段必须复用 `consumePending` 的 `{applied, resetBar}` 机制**，
不要另写一条"立即跳"的路径。理由同 §3.1：那条路径已经处理好了
`scheduler` 中途退出 + `loopStart` 重映射 + `resetTracking` 这一整套
（`scheduler` 拿到 `resetBar` 后本来就会重算 `loopStart = nextNoteTime - schedBar × S.sig × spb()`）。
另写一条 = 把那些坑再踩一遍。

## 7. ★ 需要你拍板的决策点

> 这一节是本次探针的核心产出。下面每一条都**无法从代码推出来**——是产品取舍。
> 我给建议，但建议不等于答案。**D1 最关键**，其余可以在档位① 动工后再定。

### D1 · 选哪个档位？（最关键）

> **D7 已答后的修订**：档位② 对 (a) 型段落基本没有价值（见 §0.5），
> 跳段也已从③ 下移到①′。所以现在真正的选择是 **①′ 做 / 不做**。

| 选项 | 后果 |
|---|---|
| **①′ 播放层面串联**（建议） | 2–2.5 批次。节目单 + 段落名字 + 播放范围/范围循环 + 小节边界跳段。**不动时间轴不变量**。能完整支撑"编结构 → 通练 → 单练某段 → 跳段重来" |
| ①′ + 块结构 | +0.5 批次。**只在你的主歌/副歌是 (b) 型时才需要**（见 D8） |
| ①′ + 变拍号 + 拖拽 UI | 再 +1.5–2 批次。**只在你会遇到"一首歌中途变拍号"时才需要** |
| 先不做 | 现状仍能"手动切预设 + 反复练"，曲式只是把这件事自动化 |

**我的建议：做 ①′，先不做块结构。** 等你在实际用的时候发现"主歌 8 小节的后 4 小节不一样，
表达不了"，再加块结构——它是一个**纯加法**（`sections[i].releases` 与 `blocks` 可共存）。

### D2 · 练习形态：只练某一段，还是从头走完？

> **D7 已答后的修订**：真实歌曲 40 小节 ≈ 100 秒，**段落范围播放是刚需**，不只是"可选"。
> 好消息是它比原先估计的便宜（复用 `consumePending`）。

**建议：①′ 里就带上「播放范围 + 范围循环 + 小节边界跳段」三件套。**
- **播放范围**：设定从第几段播到第几段（默认全曲）
- **范围循环**：范围内循环（单段循环是 `[i, i]` 的特例）→ 这就是"只练副歌"
- **跳段**：播放中按"跳到副歌" → 在下一个**小节**边界生效（最多 2.5 秒），
  不需要相位换算，复用现有挂起机制

**不做**：播放中"任意小节跳转"（那是另一种能力，且需要相位换算，等真需要再说）。

### D3 · 允许整首曲子里变拍号吗？

（结论不变）**建议：v2 要求整首同拍号**（哪个拍号都行，但不中途变）。
这是档位③′ 里唯一剩下的昂贵部分——`S.sig` 要从"全局唯一"变成"当前段的拍号"，
牵连拍号 pill、`updateMeta`、`meterName`、`setSig` 语义，以及 `consumePending` 里
"拍号变则等到循环起点"那条规则（段落边界 ≠ 循环起点）。
**等你真的遇到"一首歌中途变拍号"再考虑。**


### D4 · 编排入口做多全？

- **简版**（建议）：选预设 + 填重复遍数 + 上下移，存冷键。复用现有 pill/列表组件
- **完整版**：拖拽排序、段落命名、每段 BPM —— 属档位③

**建议：简版。** 但数据结构预留成以后能扩成完整版的样子（就是 §3.1 那个 `sections` 形状）。

### D5 · 「静音拍」在曲式里怎么算？（盘点时才发现的）

现在是"**每 4 小节**静音第 4 小节"，写死在四处。曲式里可能有两种解释：

- **按段**：每段的最后一小节静音 —— 语义变成"每段收尾时练内心数拍"
- **按全局**：仍然是每 4 小节静音一次（4 的倍数处），与段落边界无关 —— 改动最小

**我的建议：按全局**（保持现有语义不变），并在曲式模式下**允许直接关掉**静音拍。
理由是"按段静音"只在段长是 4 的奇数倍时才有区别，而这个区别不值得为它改四处判断。

### D6 · 练习量在曲式里按什么算？（同样盘点时才发现）

现在 `limitBars` 是全局累加。曲式里"练 8 小节"可能指整首累计 / 单段累计 / 按循环累计。

> **D7 已答后的修订**：它与 **范围循环**组合得很好，所以结论不变但仍推荐整首累计。

**建议：整首累计**（保持现有语义，零改动）。理由：
- 配合"范围循环"就自然覆盖了"单段累计"的需求：
  设成「只练副歌 + 范围循环 + 练习量 16 小节」= 副歌练 2 遍就停
- 段边界不需要额外记账，`limitBars` 那两处 `++` 一行不改
- "按循环累计"要求定义"一轮"（整曲一遍？范围内一遍？），多一份语义没多一份价值

### D7 · 从你那边需要的信息

~~你实际在练的是什么结构？~~ **已回答：真实歌曲结构**
（前奏 4 → 主歌 8 → 副歌 8 → 间奏 → 主歌 → 副歌）。见 §0.5 的三点确认与两处结论修订。

### D8 · 你的「主歌 8 小节」，后 4 小节和前 4 小节一样吗？（新问题，只在 D7 已答后才出现）

**这是 D7 的答案直接带出来的问题**（见 §0.5）：

| | 情况 | 现在能表达吗 | 要不要做块结构 |
|---|---|---|---|
| **(a)** | 同一个 4 小节伴奏型放 2 遍 | ✅ 能（`repeats: 2`） | **不用做** |
| **(b)** | 第 5–8 小节与第 1–4 **不一样**（两个不同乐句） | ❌ 不能（预设上限就是 4 小节） | **要做**（+0.5 批次） |

**怎么判断自己是哪种**：你弹主歌时，第 5–8 小节手上弹的东西与第 1–4 小节**是不是同一套**？
- 弹唱伴奏（一个扫弦型一直弹 8 小节）→ (a)
- 有单独的前 4 / 后 4 乐句设计（比如 4 小节和弦行进 + 4 小节变奏）→ (b)

**建议：先在 ①′ 里只做 (a)。** 块结构是**纯加法**（`blocks` 与 `repeats` 可以共存），
等真表达不了再加，不必现在为它多花 0.5 批次。
