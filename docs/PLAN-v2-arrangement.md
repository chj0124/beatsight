## 1. 为什么不能"顺手加上"

现在的音频核心是：**一个节奏型 + 一个 4 小节循环 + 一个时间轴锚点**。这三件事是互相咬合的：

```
loopStart ────┬── 小节 0 ── 小节 1 ── 小节 2 ── 小节 3 ──┐
              └──────────────── 回到小节 0 ──────────────┘
              nextNoteTime == loopStart + tick × spb/TPB   ← 核心不变量
              appliedPat = 当前那个节奏型（唯一）            ← 核心假设
```

曲式要的是：`[前奏 ×4] → [主歌 ×8] → [副歌 ×8]`。这等于要求**"循环什么"本身也要有时间结构**——
于是"4 小节"从"世界的尺寸"变成了"段落的属性"，而**时间轴锚点、发声快照、渲染行数、视觉追踪**
四样东西都建立在"世界的尺寸是 4"之上。

不是不能改，而是**改动会沿这四条线扩散**——所以先盘清楚有哪几条线。

## 2. 事实盘点：严格 4 小节循环 = 17 条假设

`LOOP_BARS = 4` 是唯一常量，但它的**语义**散落在 17 处。按"曲式化后要不要动它"分三档标注：

| # | 现在的假设 | 位置（函数 / 常量） | 档位① | ② | ③ |
|---|---|---|:--:|:--:|:--:|
| 1 | 小节游标在 `0..3` 环绕 | `Audio.scheduler` 的 `schedBar = (schedBar+1) % LOOP_BARS`（**两处**：正常小节边界 + 空小节跳过分支） | ✎ | | |
| 2 | 单锚点时间轴，`nextNoteTime == loopStart + tick × spb/TPB` | 整个 `Audio` 模块；`Controls.setBpm` 靠它算相位锚点 | ✎ | | ✎ |
| 3 | 发声用**单一**节奏型快照 | `activePattern()` / `Presets.applyPatternChange` 的 `appliedPat` | ✎ | | ✎ |
| 4 | 反推小节起点并向前看最多 4 小节 | `Audio.predictNext`（`for k < LOOP_BARS`） | ✎ | | ✎ |
| 5 | 弹跳球接力：下一行 = `(bar+1) % 4` | `Viz.paintBall` 的待命球分支 | ✎ | | |
| 6 | 静音拍固定静音**第 4 小节** | `Viz.buildViz` / `Viz.resetForStop` / `Audio.scheduler` / `Viz.paintFrameBody`（**四处**都判 `bar === LOOP_BARS-1`） | ? | | |
| 7 | 同屏固定渲染 4 行 | `Viz.buildViz`（`for b < LOOP_BARS`） | | ✎ | |
| 8 | 播放位置对 `meter × 4 × TPB` 取模求行号 | `Viz.paintFrameBody` 的时钟回落分支；`audioPosAt` | | ✎ | |
| 9 | 就地接续对 `barTicks × LOOP_BARS` 取模 | `Audio.resyncToNow` | ? | | ✎ |
| 10 | 拍号变更等到「循环起点」（`schedBar === 0`） | `Presets.consumePending(schedBarNow)` | ✎ | | ✎ |
| 11 | 预设必须正好 4 小节 | `Store.validatePreset`（`bars.length !== LOOP_BARS` 直接拒） | — | | |
| 12 | 编辑器固定 4 行 | `Editor.render` | — | | ✎ |
| 13 | 练习量按小节累加 | `Audio.scheduler` 的 `limitBars++`（两处） | ? | | |
| 14 | 变速训练器每 N 小节升速 | `Trainer.onBarBoundary`（由 `scheduler` 小节边界调用） | ? | | |
| 15 | 切换后清视觉追踪 | `Viz.resetTracking()` + `onsetBuf.length = 0` | ✎ | | |
| 16 | 可视化标题写死「同屏 4 小节」 | **两处**：静态标记 `#vizTitle` + `Viz.buildViz` 末尾的赋值 | — | ✎ | |
| 17 | 全局唯一拍号 `S.sig` | 全局；牵连拍号 pill、`updateMeta`、`meterName` | — | | ✎ |

`✎` = 必须改 ｜ `?` = **出现了一个新的产品问题**（见 §7 的 D5 / D6）｜ `—` = 不受影响

**三个最值钱的行是 4、5、6**，它们不是"改个数字"，而是**语义要重新定义**：

- **#4 / #5**：`predictNext` 和待命球都只看得到当前这个 4 小节循环。曲式里，**段落最后一小节**
  需要"看到"下一段的第一个音——否则球在段落边界会停住、待命球没有目标。
  这不是把 `LOOP_BARS` 换成"当前段长度"就行：它要求预测能**跨段**。
- **#6**：「静音拍 · 每 4 小节静音第 4 小节」在曲式里是什么？按段静音（每段最后一小节）？
  还是保持"全局每 4 小节"？**这是一个你现在还没想过、但必须在动工前定下来的产品问题。**

## 3. 三个档位详述

### 3.1 档位① 播放层面串联（最小）

**数据模型**（新增冷键 `beatsight.arrange`）：

```js
{ name: "xxx", v: 1,
  sections: [
    { ref: { type: "builtin", idx: 0 }, repeats: 4 },   // 前奏，放 4 遍（= 16 小节）
    { ref: { type: "custom",  id: "c1758..." }, repeats: 8 },
  ] }
```

`ref` 的形状**刻意复用现有 `S.sel`**（`{type:"builtin", idx}` / `{type:"custom", id}`）——
这样"从曲式里挑一段"和"直接选预设"是同一套解析逻辑（`selectedPreset()`），不必再写一份，
也不会出现"曲式里的段"与"当前预设"两套边界不一致。

**播放**：新增两个会话游标 `arrIdx`（第几段）+ `arrBar`（段内第几小节）。
小节边界处：`arrBar++`；放满 `sections[arrIdx].repeats × LOOP_BARS` 后 `arrIdx++`，
并把下一段交给 `applyPatternChange`。

**段落切换用「小节边界挂起」**（`Presets.consumePending` 的泛化）——
不用 `resyncToNow`（相位就地接续）。理由：
- 段落切换**天然发生在小节边界**（段长是 4 的整数倍），不需要"中途插进去"
- `resyncToNow` 是给"用户在播放中随手点了个别的节奏型，希望立刻生效"用的；
  它的相位换算在小节末会顺延到下一小节（已有 `j < 0` 分支），**语义上就是"尽量接近边界"**
- 挂起路径已经处理好了"scheduler 中途退出 + `loopStart` 重映射 + `resetTracking`"这一整套
  （`consumePending` 返回 `{applied:true, resetBar}`），复用它比自己再写一条便宜得多

**可视化**：仍是 4 行——就是当前那一段的 4 小节。`buildViz` / `paintFrameBody` 一行不用改。

**必须处理的边界**：`predictNext` 与待命球在**段末**要能看下一段（#4 / #5）。
做法：把"向前找下一小节"的步进从 `(schedBar + k) % LOOP_BARS` 改成
"沿节目单步进"（段内 +1，段末跳到下一段第 0 小节）。这是一个**局部改动**，
但它必须与 `scheduler` 的游标推进用**同一个函数**——否则预测与实际排程会在段末分叉，
而那正是 T22/T30 一直在守的东西。

**拍号**：档位① 要求**整首同拍号**。相邻两段拍号不同的曲式在保存时直接拒绝并提示原因。
（现有 `consumePending` 的 `sigChgPending` 逻辑是"拍号变则等到 `schedBar === 0`"，
段落边界与循环起点不重合时这条规则需要重新定义——那是档位③ 的活。）

**编排 UI（简版）**：训练模式区或预设区新增一个入口 → overlay 列表：
「选预设（复用预设库）+ 填重复遍数 + 上移/下移 + 删除」+ 一个「从头播 / 只播选中的段」。

**代价**：1.5 – 2 批次。改动集中在 `Audio.scheduler`（游标）、`Presets`（挂起泛化）、
一个新冷键 + 一个简版 UI。**不碰时间轴不变量**（#2 保持原样，只是 `appliedPat` 会在段边界换人）。

**受影响测试**：T12（小节边界无缝切换）、T15（切拍号）、T20（点下即生效）、
T21（9×9 组合 × 3 相位全量扫描）、T48（练习量按小节）。
这些守的都是"切换"这件事，档位① 动的是同一处逻辑 → **必须逐条重跑并确认不变量仍成立**。

---

### 3.2 档位② 段落自适应可视化

在① 之上让"同屏小节数"随段落变：一段 8 小节就画 8 行。

**改动**：`Viz.buildViz`（行数由当前段长决定）、`Viz.paintFrameBody`（行号映射、进度换算）、
`vizTitle` 文案、以及**桩的几何模型**——
测试沙箱里 `_rowTop = 58 + i × 86` 是"按创建序分层"的硬编码假设，行数变化要让它跟着支持
（否则弹跳球的位置断言全是假的，而假绿比没测更糟）。

**风险点**：行数多了以后，在 390px 窄屏上 8 行 × 86px = 688px 高，加上顶部 58px 空域，
一屏放不下。**这不是渲染 bug，是设计取舍**——要么滚动、要么缩小行高、要么按屏高自适应。

**代价**：+1 – 1.5 批次。**不动音频**，纯渲染层。

---

### 3.3 档位③ 完整曲式编辑器

在② 之上再加：

- **独立的全屏编排 UI**：拖拽排序、段落命名、每段重复遍数 + 每段 BPM
- **变拍号**：`S.sig` 从"全局唯一"变成"当前段的拍号"。这一条牵连很广：
  拍号 pill 的选中态、`updateMeta`、`meterName`、`Controls.setSig` 的语义、
  以及 `consumePending` 里"拍号变则等到循环起点"那条规则（段落边界 ≠ 循环起点）
- **任意跳段**（不只顺序推进）：这是对 `resyncToNow` 的泛化——
  要能在"主歌第 3 小节"直接跳到"副歌第 1 小节"，且不排到过去、不跳针

**代价**：再 +2 – 3 批次。**这是唯一会动时间轴不变量的档位**，也是返工风险最集中的档位。

## 5. 分阶段落地路径（推荐）

```
① 播放层面串联         → 可独立发布（v2.0.0）  覆盖"练一首歌"八成需求
   ├─ ② 段落自适应行数   → 可独立发布（v2.1.0）  纯渲染，不动音频
   └─ ③ 完整编辑器       → 可独立发布（v2.2.0）  动时间轴与拍号语义
```

**为什么按这个顺序**：

1. ① 完成时就已经能"把一首歌编出来并从头练到尾"，这是你提出这个需求时想要的东西
2. ② 是纯渲染改动，**不碰任何时间轴逻辑**，风险与 ① 正交
3. ③ 才是真正危险的那一档（动 `S.sig` 语义 + 任意跳段），
   而它带来的增量体验（变拍号、拖拽编排）**只有在①②都稳定之后才值得为之冒返工风险**
4. 每一步都能单独发布 → 任何一步效果不好都能停下，不会"箭在弦上"

**关键做法**：① 里那个"沿节目单步进"的函数必须**只有一份**，被 `scheduler`（实际排程）和
`predictNext`（预测）共用。这是 ① 里唯一容易埋雷的地方——预测与实际分叉会同时打坏
弹跳球、播放头、和待机球的交接。

## 6. 风险与缓解

| # | 风险 | 后果 | 缓解 |
|---|---|---|---|
| R1 | `predictNext` 与 `scheduler` 在段末分叉 | 球在段落边界停住/乱跳；播放头与实际发声错位 | 两者共用同一个"沿节目单步进"函数；T22 新增段末断言 |
| R2 | 段落切换时 `onsetBuf` / 视觉追踪没清 | 球分叉、残留高亮 | 复用小节边界挂起那条已验证的路径（它已经做了 `resetTracking` + `resetBar` 重映射） |
| R3 | 段末 + 变速训练器 + 练习量三者在同一小节边界叠加 | 优先级混乱、文案错 | 明确顺序（与 v1.9.0 的"谁先到谁停"同一套处置），写成文档 + 断言 |
| R4 | 段长非 4 的整数倍（若以后允许） | 所有 `% LOOP_BARS` 假设同时崩 | **v2 明确要求段长 = 4 的整数倍**（`repeats` 整数），把它写进校验 |
| R5 | 曲式引用了一个被删掉的自定义预设 | 播放到那一段时无型可放 | 加载与保存时校验引用；播放时失效则跳过并提示（参照 `curPattern()` 的 `basicPattern` 回退） |
| R6 | ② 的多行可视化在窄屏一屏放不下 | 需要滚动或缩小行高 | 先出窄屏截图定方案；**这是设计取舍不是 bug**，别在实现阶段临时决定 |
| R7 | ③ 的 `S.sig` 语义变化波及整个 UI | 拍号 pill / `updateMeta` / `meterName` 全线要审 | ③ 动工前先做一次"`S.sig` 全部读取点"的盘点（同本文档 §2 的做法） |

## 7. ★ 需要你拍板的决策点

> 这一节是本次探针的核心产出。下面每一条都**无法从代码推出来**——是产品取舍。
> 我给建议，但建议不等于答案。**D1 最关键**，其余可以在档位① 动工后再定。

### D1 · 选哪个档位？（最关键）

| 选项 | 后果 |
|---|---|
| **① 最小**（建议） | 1.5–2 批次。能编曲式、能从头练到尾、每段反复练。可视化仍是 4 行；整首同拍号 |
| ① + ② | +1–1.5 批次。段落长的曲子能一眼看全。窄屏需要额外做取舍 |
| ① + ② + ③ | 再 +2–3 批次。任意跳段、每段调速、变拍号。**唯一动时间轴不变量的档位** |
| 先不做 | 现状已经能"手动切换预设 + 反复练"，曲式只是把这件事自动化 |

**我的建议：先只做 ①。** 它不动时间轴不变量（风险最集中的地方），且完成即覆盖主要需求。
做完用一阵子再决定要不要 ②。

### D2 · 练习形态：只练某一段，还是从头走完？

- **段落循环优先**：能锁定"只练主歌"，反复 N 遍后自动切下一段 —— 更贴"练习工具"
- **顺序推进优先**：从头到尾不中断，当伴奏用

影响：前者要求"任意跳段"（档位③ 的能力），后者档位① 就够。
**建议：① 先做顺序推进 + "只播选中的那一段"（不做任意跳转）**，够用且便宜。

### D3 · 允许整首曲子里变拍号吗？

- **要求同拍号**（建议）：便宜。段边界就是循环边界。
- **允许变拍号**：现有挂起机制是"拍号变 → 等循环起点"，而段落切换的时点不再与循环起点重合，
  两套语义会缠在一起 —— 这是档位③ 里最贵的一块。

**建议：v2 要求整首同拍号**（哪个拍号都行，但不中途变），变拍号留到 v2.1 或更后。

### D4 · 编排入口做多全？

- **简版**（建议）：选预设 + 填重复遍数 + 上下移，存冷键。复用现有 pill/列表组件
- **完整版**：拖拽排序、段落命名、每段 BPM —— 属档位③

**建议：简版。** 但数据结构预留成以后能扩成完整版的样子（就是 §3.1 那个 `sections` 形状）。

### D5 · 「静音拍」在曲式里怎么算？（盘点时才发现的）

现在是"**每 4 小节**静音第 4 小节"，写死在四处。曲式里可能有两种解释：

- **按段**：每段的最后一小节静音 —— 语义变成"每段收尾时练内心数拍"
- **按全局**：仍然是每 4 小节静音一次（4 的倍数处），与段落边界无关 —— 改动最小

**我的建议：按全局**（保持现有语义不变），并在曲式模式下**允许直接关掉**静音拍。
理由是"按段静音"只在段长是 4 的奇数倍时才有区别，而这个区别不值得为它改四处判断。

### D6 · 练习量在曲式里按什么算？（同样盘点时才发现）

现在 `limitBars` 是全局累加。曲式里"练 8 小节"可能指：

- **整首累计**（保持现有语义）—— 改动最小
- **单段累计**（每段单独到点停）—— 更适合"只练主歌"
- **按循环累计**（放完整首算一轮）

**我的建议：整首累计**，保持现有语义。与 D2 的选择一致：① 不做任意跳段，所以"单段累计"没有意义。

### D7 · 从你那边需要的信息

**你实际在练的是什么结构？**

- 「前奏 4 → 主歌 8 → 副歌 8 → 间奏 → 主歌 → 副歌」这种**真实歌曲结构**
- 还是「两三个和弦循环，但想分段练」

**这个答案会决定档位① 到底够不够。** 如果只是后者，可能连曲式都不需要——
加一个"**段落循环区间**"（指定从第几小节循环到第几小节）就够了，成本不到 ① 的一半。
