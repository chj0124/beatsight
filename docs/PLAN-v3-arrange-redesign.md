## 0. 拍板结论（2026-09-26 用户已答）

| 决策点 | 结论 |
|---|---|
| T1 范围模型 | **保持** `from/to/loop` 三件套，不升级为多范围保存 |
| T2 段落语义 | 本期**不加**段落类型标签；数据模型随段 uid 顺带预留扩展面 |
| T3 变拍号 | **维持整首同拍号**。用户确认存在变拍号曲目但很少见——不为此动 `S.sig` 全局语义（当初档位③唯一遗留的昂贵项），未来若做，立项起点是「拍号入段」而非改全局 |
| T4 歌词错位修复 | **单独先行**（阶段一），与后续阶段风险隔离 |
| T5 换型候选组织 | 按节拍/扫弦/自定义**三区组织** + 当前型置顶，不加搜索框 |
| 侧栏「整首连播」 | **接受条目合并**（阶段三） |
| 优先级 | **G3（歌词错位）→ G2（编辑效率）→ G1（入口收敛）**；G4（逐段试听）成本极低，作为阶段二附属项一并评估 |

### 用户已确认的现状盘点（本方案的事实基础）

- 歌词行按 `(arrangeId, 段下标)` 寻址（`Store` L2951–3023）——段上移/下移/删除后全部错位，**真实缺陷**。
- 「整首连播」按钮与曲式条目**已经**调用同一 `playArrange(a)`（L8152、L8417）——合并删按钮，信息无损转移。
- `demoSongNote`（「播放中 · 第 N/总 小节」）是播放位置的**唯一文字面**（L8496–8499，T68j 钉住）——删按钮必须保留并升级这行读数。

## 2. 阶段一 · 段稳定 uid（G3）

### 2.1 数据模型与迁移

```js
// 曲式（normArrange 输出）——新增 uid 字段，其余不变
section = { uid: "s1698…-3", name: "主歌", blocks: [ { ref, repeats } ] }

// 歌词行——寻址键从段下标改为段 uid
lyricLine = { arrangeId: "a…", secUid: "s1698…-3", chars: [{ t, dur, ch }] }
```

**uid 生成**：沿用 id 惯例 `"s" + Date.now() + "-" + (secSeq++)`（同 `arrSeq` 模式）。判重与补发规则在 `normArrange`：

| 情形 | 处理 |
|---|---|
| 段无 uid | 补发 |
| 同曲式内 uid 重复 | 后者重发 |
| uid 非字符串/空 | 重发 |

**歌词冷键迁移（`KEY_LYRICS`，`v:1` → `v:2`）**，加载期一次性完成：

```
旧行 {arrangeId, sec: 2, chars}：
  ① 该行已有 secUid → 直接用（幂等，重复加载不重复迁移）
  ② 按 sec 下标取曲式 sections[2].uid → 改写为 secUid
  ③ 下标越界（段已删）→ 按段名匹配一次 → 仍失败 → 丢弃并计数（口径同既有"坏行丢弃记 warn"）
  ④ 同 (arrangeId, secUid) 多行 → 留第一条（既有口径）
```

★ **语义声明（必须写进 CHANGELOG 与注释）**：迁移把"当前的下标对应关系"冻结为 uid 绑定——
它修复的是**未来不再错位**，不追溯修复历史上已经错位的歌词（那需要用户人工核对，机器无从判断本意）。

### 2.2 函数级改动清单

| 位置 | 改动 |
|---|---|
| `Store.normArrange`（L2713） | 输出 `sections[].uid`；补发/重发逻辑（上表） |
| `Store.normLyricLine`（L2951） | 形状校验改 `{arrangeId, secUid}`；兼容读入旧 `sec` 字段交给迁移层 |
| `Store` 加载段（L2981–2999） | 迁移流程 ①–④；`persistLyrics` payload 升 `v:2` |
| `Store.findLyric / upsertLyric / deleteLyric`（L3003–3023） | 签名 `(arrangeId, secIdx)` → `(arrangeId, secUid)` |
| `Store.findLyricByUid` 之外的调用方换算 | `Arrange` 模块内所有传 `i`（段下标）的歌词调用点：`distribute`、`mkLyricRow`、`onDragEnd`、`ensureDemo`、`loopLyricSection` —— 内部 `a.sections[i].uid` 取一次再传 |
| `lyricSpanTicks / lyricCharsAt`（L4297/4310） | 签名改 secUid；内部 `sections.findIndex(s => s.uid === secUid)`；找不到 → span 0（既有口径：不判越界，交给 arrangeProblems） |
| `Arrange.buildSecRow / mkLyricRow` | 歌词轨按 uid 取行；aria-label 文案不变 |
| `loopLyricSection`（L10354） | 收 secUid（或内部换算）；`byLyric` 语义不变，身份更稳 |
| `demoBuildSpec` 歌词写入（`ensureDemo` L10426） | `upsertLyric(v.id, sections[i].uid, chars)` |

**不动的**：`arrNextBar` / `songBarAt` / `secBars` / 调度 / 渲染窗口——它们只看 blocks，从不看下标寻址的歌词。

### 2.3 测试计划

**新增 `t103-lyric-sec-uid.js`**（契约测试）：

1. 段下移后歌词跟随该段（旧数据下标键必红、uid 键必绿——本条即反向验证的主断言）
2. 段删除后其歌词行不可见、被删段后方的歌词仍挂原段
3. 旧格式冷键（`sec` 下标）加载迁移 → uid 绑定正确、持久化写出 `v:2`
4. 迁移幂等：同一冷键加载两次结果一致
5. 下标越界行 → 按段名匹配成功/失败两路
6. `loopLyricSection` 按 uid 定位段，段重排后仍循环正确的段

**必须全量重跑**：t51（段长/游标）、t52（节目单纯函数）、t55（使用方法文案——若提及歌词寻址）、t66（playMode 契约）、**t68 全家**（侧栏滑块+歌词轨读数）、t88（范围滑块）、t91（迁移矩阵——**加一行本迁移**）。

## 3. 阶段二 · 编辑效率（G2 + G4）

### 3.1 模板新建

「新建曲式」改为小菜单（四选项，纯数据预填，零新机制）：

| 模板 | 预填结构 |
|---|---|
| 空白 | 一段 × 1 块 × 1 遍（=现默认） |
| 主副歌骨架 | 主歌 8 + 副歌 8（各 1 块 × 8 遍，型取当前选中型） |
| 完整流行曲式 | 前奏 4 + 主歌 8 + 副歌 8 + 间奏 4 + 主歌 8 + 副歌 8（6 段） |
| 复制当前曲式 | 深拷贝 + 改名"xxx 副本" |

实现：模板常量 + `buildTemplateArrange(kind)`，产物直接过 `Store.upsertArrange`（校验边界自动兜）。
**注意 v2.13.0 首开默认值契约**：默认选中示例曲的初始化逻辑不受新建菜单影响（新建菜单只在 overlay 内可达）。

### 3.2 块胶囊就地换型（T5）

现状：块 = [型名][遍数 input][换][✕]，点「换」→ 段行下方插候选行（`picking`/`pickPill`，L10127–10155）。

重设计：

1. 块合成**单胶囊** `[型名 ×N 遍]`（型名 + 遍数合并显示，遍数仍可点改——保留原 input 或胶囊双击改数，动工前按节点预算二选一，见 §6 R2）。
2. 点胶囊 → 候选**就地展开在胶囊正下方**（沿用 v2.4.1"候选与触点同视野"的既定结论），组织为**三区**（节拍/扫弦/自定义，与侧栏同构），**当前型置顶高亮**，键盘 Tab 可达 + Enter 选中。
3. `picking` 状态机保留（仍是 {sec, blk}），`pickPill` 改为分区渲染；候选行 DOM 属运行时生成，不占静态预算。

### 3.3 段操作：移到首/尾

段操作钮由 `[起][终][↑][↓][✕]` 扩为 `[起][终][↑][↓][⤒][⤓][✕]`（图标钮，aria-label 写明）。
纯数组操作，与既有 `mkMove` 同一助手模式。**不做自由拖拽排序**——测试桩驱动不了自绘拖拽（v2.10.4 既定结论），四钮覆盖 90% 场景。

### 3.4 复制曲式

曲式库条目区加「复制」pill（与「新建/删除」并列），深拷贝 + 副本命名（重名自动加"副本/副本2"…）。
导出/导入的 `normArrange` 天然兼容（uid 重发规则兜底——导入的曲式 uid 与库里冲突时重发，歌词行不随导入复制，与既有"导出整包"语义一致）。

### 3.5 G4 逐段试听（附属项）

段行加「▶」mini 钮：**只放这一段一遍** = 范围设该段 + `loop:false` + `playQuota = 该段小节数`（复用 v1.10 听辨训练的会话额度机制——v2.10.12 后它是"到点停"唯一消费者，机制现成且与调度同源）。不动 `loopLyricSection`（那是"循环+爬坡"的另一语义）。

### 3.6 测试计划

**新增 `t104-arrange-editor-v3.js`** + `t105-arrange-templates.js`：

1. 模板四条路 → 段/块结构断言（过 `normArrange`）
2. 复制曲式 → 副本独立（改副本不影响原曲式：blocks 深拷贝断言）
3. 块胶囊点选 → 候选三区结构 + 当前型置顶 + 就地位置（触点同视野）
4. 移到首/尾 → 数组序 + 歌词（uid 键）跟随
5. 逐段试听 → arrangeSel/loop/quota 三件套断言，播完自停

**必须全量重跑**：t51/t52/t65、t57（编辑器入口契约）、t63/t68 系、t93（首开默认）、**t45 系 DOM 预算与 smoke.js**（候选三区为运行时 DOM，静态标记净增 ≤4）。

### 3.7 反向验证变异清单

| 变异 | 必须红的断言 |
|---|---|
| 模板预填绕开 `upsertArrange` 直写库 | t105 #1 结构校验 |
| 复制曲式浅拷贝 blocks | t105 #2 副本独立性 |
| 候选区删"当前型置顶" | t104 #3 置顶断言 |
| 试听删 `playQuota` 设置 | t104 #5 播完自停（只循环一遍） |

## 4. 阶段三 · 入口收敛（G1）

### 4.1 删「整首连播」按钮，读数升级

**事实基础**（已核实）：曲式条目点击**已经等于**播放整首（L8152，v2.5.0 起）——「整首连播」按钮是同一 `playArrange(a)` 的第二入口（L8417 注释自己列了两个调用方）。唯一不能丢的是**状态指示**：

| 现状职责 | 去向 |
|---|---|
| 按钮 `active` 高亮（`whole` 判据，L8491–8495） | 由读数文案承担（下） |
| `demoSongNote` 读数（T68j 钉住，**保留**） | 播放中分支补 whole 判定：`整首连播 · 播放中 · 第 N/总 小节`（非整首范围维持现状文案） |

**函数级改动**：

| 位置 | 改动 |
|---|---|
| `Presets.buildDemoSongRow`（L8361–8411） | 删 `btn`（`demo-play-row` 行保留，只放 `note` 读数；行改名或保留类名——t68 定位按类名，**类名不动**） |
| `demoPlayAllBtn` 引用、`syncDemoRange` 的 whole 高亮段（L8492–8495） | 删除；`whole` 变量保留（读数文案要用） |
| `playArrange` | 不动（条目点击仍是它） |
| 使用方法页（help） | 「整首连播」词条改写：入口=点曲式条目；状态看读数行。t55 内容契约同步 |
| README「核心交互细节」 | 同步改写 |

**零交互损失论证**：条目点击（播整首）+ 读数行（状态）= 原按钮的全部用户价值；少一个与条目等价的按钮，少一处"两个入口同一动作"的认知负担。

### 4.2 测试计划

**新增断言进既有用例**（不新开文件，改动面小）：

- t68 系：删按钮后容器结构、`note` 读数三分支（整首已就绪 / 整首播放中 / 局部范围）
- t55：help 词条更新

**必须全量重跑**：t63/t68/t73/t74/t75/t88/t89/t93、t45 系 + **smoke.js**（节点数只减不增，预算不动）。

## 5. 不做的事（明确排除）

| 排除项 | 理由 |
|---|---|
| 变拍号（拍号入段） | 用户确认极少见；动 `S.sig` 全局语义是全项目最贵单点。未来立项起点：段级 meter 字段 + `consumePending` 规则重定义 |
| 段落类型标签 | 本期无消费者（跳段按类型/变速按类型都是下一个立项） |
| 多范围命名保存 | 伪需求：练法多变，"当前范围"只有一个 |
| 自由拖拽排序（段/块） | 测试桩驱动不了自绘拖拽；四钮方案已覆盖 |
| 换型搜索框 | 12 内置 + 少量自定义的规模下过度设计 |
| 曲式库标签/文件夹 | 已有 v2.25.0 分组能力（📁/拖拽归组），不重复建设 |
| 单条曲式导出 | 「导出全部数据」整包已覆盖，低频 |

## 6. 风险与缓解

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 歌词迁移误把"已错位的现状"固化 | §2.1 语义声明写进 CHANGELOG：修复未来错位，不追溯历史；帮助页补一句"段大改后建议核对歌词" |
