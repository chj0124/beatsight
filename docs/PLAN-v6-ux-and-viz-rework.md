## 2. 变更协议（偏差纠正机制）

**前提认知：偏差一定会再出现，尤其在批 C（热路径）与批 F（需实测）。机制的价值不是消灭偏差，
而是让每个偏差在「一句话就能修」的阶段被截住。** 按严重度分三级：

- **Ⅰ 级 · 实现细节偏差** —— 行号漂移、选择器改名、注释与代码不符但行为一致等。
  **自行适配，在该批完成报告里如实报备，不停下打扰用户。**
- **Ⅱ 级 · 方案级偏差** —— 方案依赖的假设不成立 / 需换做法（用户目标不变）。
  **该项立即暂停，同批其余项继续。** 给出：偏差说明 + ≤2 个候选做法 + 我的推荐，**用户拍板后才动**。
  绝不「将错就错」，绝不擅自扩大改动范围。
- **Ⅲ 级 · 目标级偏差** —— 需求本身与现有机制冲突，或发现明显更好的实现路径。
  **整批暂停，回到方案讨论。**

### 2.1 落到操作上的四个具体做法

1. **每批开工前做「假设复核」**：把该批每项依赖的事实断言（如「曲式块存引用非快照」「下拉关时禁用」）
   **逐行重读代码**核对——不凭上一轮记忆。核对结果先交付用户（§7 是批 A 的样板）。
2. **批次本身就是预留空间**：6 批各自独立、各自 check-all 全绿、各自可回滚。任一批出 Ⅱ 级偏差，
   已完成的批不受污染，未开始的批按修正后的认识调整。
3. **批末报告 = 用户的纠正窗口**：每批交付三样东西——`check-all` 实际输出、**「方案 vs 实际」差异清单
   （含所有 Ⅰ 级）**、按仓库风格写的 commit message 草稿。改动**不 push**，纠正成本仅限本地。
4. **反向验证兜底行为偏差**：缺陷修复与行为变更类（1.5 / 2.3 / 2.5 迁移）按仓库惯例做反向验证——
   回退改动后目标断言应变红。抓「以为改对了其实没生效」与「生效了但改错地方」两类隐蔽偏差。

### 2.2 每批通用执行纪律（逐批 checklist）

- [ ] bump `index.html` 的 `const VERSION`；`package.json` + `package-lock.json`（`npm install --package-lock-only`）
      + `CHANGELOG.md` 首条 `## vX.Y.Z` 三处对齐（`check-version.js` 强制）。
- [ ] **改动过 `index.html` 行数后，必须 `node tools/gen-index.js --write`**——模块索引行号被
      `check-docs.js` 第 1 项逐一比对，任何插入/删除行都会让索引漂移（本批每项都会碰到）。
- [ ] 新增测试沿用现有命名，注册进测试运行清单；缺陷修复类做反向验证。
- [ ] 帮助文档/说明文案同步（`t102` 系列有「设置里的每一项」内容契约）。
- [ ] `node tools/check-all.js` **全量全绿**（提交前；迭代中可 `--quick`）。口径：`⊘` = 未执行不算失败；
      出现第一个 `✗` 之后的一切结论不成立，从第一个 `✗` 修起。
- [ ] 交付 commit message 草稿（根因→修法→取舍→自验数字），**不 push**。

## 4. 分批详细方案

### 批 A · v2.69.0 顶栏与设置收口

#### 4.A.1 主题图标按钮（1.1）
- **做法**：顶栏「后台保活」（`#keepAwakeToggle`）右侧新增图标按钮。**沿用 `#themeToggle` 这个 id，
  把元素从设置弹窗移到顶栏**——这样 `applyTheme` 的接线、`beatsight.theme` 冷键、点击回调全部不动。
- **必须改的两处**：`applyTheme` 里原先写 `#themeToggle.textContent`（文案「主题 · 经典 / 日间」）的语句
  改为**切图标（月亮↔太阳）**；`aria-pressed` 语句保留不变。图标内联 SVG，配 `aria-label="切换到日间/经典主题"`。
- **配色**：日间主题（`body[data-theme="obs"]`）下补一条图标按钮配色覆盖。
- **窄屏**：顶栏在窄屏会换行/收缩，新增两项需在 390 / 560 / 960 三档人眼核对密度。
- **移除**：设置「外观与辅助」里的 `#themeToggle`。
- **测试影响（复核实证，见 §7）**：改 `t30`（文案断言）、`t125`（文案断言）、`t90`（把 `themeToggle`
  从"设置弹窗内 id 清单"移除）、`t57`（把用作"弹窗内元素"的 target 换成弹窗内另一 id）。
  `t92`（点击切换→壁纸重绘）因 id 与监听保留而**自动保持绿**。
- **闸门注意**：`t24` 断言顶栏内**不得出现 `class="chip"`**（且 `role="switch"` 恰好 11 处）；
  新增的延迟读数**不得用 `chip` 类**，主题按钮**不得加 `role="switch"`**。
- **文档**：帮助「设置里的每一项」主题条 + 概述里"主题在设置里"的说法同步改为"顶栏"。

#### 4.A.2 延迟补偿读数直达（1.2）
- **做法**：`#settingsBtn` 左侧加读数（建议类名 `lat-chip`，避开 `chip`），点击 = `Settings.open()` +
  滚动到「音频延迟补偿」组 + 短暂高亮该组。`Settings.open(anchor)` 加可选锚点参数；
  弹窗容器（`.dialog-panel`，`overflow-y:auto`）用**设置 `panel.scrollTop`** 定位，避免 `scrollIntoView`
  带动底层页面。
- **刷新点**：延迟有单一同步函数 `latApply()`（init 与保存后调用）。**注意**：滑杆拖动输入处理器
  只更新数值显示、不落盘也不走 `latApply` → 读数需在 `latApply` **与**输入处理器两处刷新，
  否则拖动时读数不动（或明确定档为"松手才刷新"，取二者之一，在批报告里写明取舍）。
- **0ms**：常显灰色（D2）。
- **测试影响**：`t95`（延迟补偿）与 `t102b`（延迟帮助文案）只要**不动其断言的文案/结构**即保绿；
  新增 `t136-latency-chip`。
- **注释**：顶栏现有"别再往顶栏加第二个状态/版本类元素"的注释需更新——读数是**控件**（可点击→设置），
  不是重复的状态/版本元素。

#### 4.A.3 诊断/安装入口搬迁（2.2）—— **Ⅱ级，复核后升级**
- **用户提问的答案（已实证）**：「复制诊断信息」（写剪贴板）与「导出诊断信息」（下载 .txt）
  **内容同源**（同一份诊断报告），**投递方式不同**；且导出在无下载能力时会**回退调用复制**。
  ⇒ **不是重复功能**，但入口该合并。
- **做法**：设置「诊断与自验」组改为并排两按钮「复制诊断信息 / 导出诊断信息（.txt)」；
  「安装到本机」移入设置「数据与说明」组（`beforeinstallprompt` 未触发时仍 `hidden`）。
  帮助页那节删按钮、留一句"在设置里"的指引。
- **Ⅱ级发现（复核实证，见 §7）**：`#helpInstallBtn` 的**显隐刷新点与 Help 渲染耦合**——
  `beforeinstallprompt` 到达后需**重新打开 Help** 才会刷新显隐。搬到设置后，"搬块不换 id、接线不动"
  **不成立**：显隐/点击逻辑要从 `Help` 迁到**设置打开路径**；且 `t132` 整条复用例围绕 Help 的
  挂载/显隐/点击，**需重写**。→ 动工前需用户确认迁移落点（建议：装配层加 `refreshInstallVisibility()`，
  在 `Settings.open` 时调用）。
- **不受影响**：`t56`（`diagCopyBtn` 在设置、关闭再开文案复位）与 harness 的 `diagCopyBtn` 桩。

#### 4.A.4 新建分组图标（2.4）
- **做法**：`.sec-add` 的 `::before` 全角「＋」换成内联 SVG 圆圈加号（data-uri）。
- **安全边界（已实证）**：`sec` 元素的 `textContent` 逐字有铁律（`t63`/`t84b` 盯着），
  但 `.sec-add` 是**独立按钮**、无文字节点，`t101` 按 `className === "sec-add"` 找它
  ⇒ **纯 CSS 改动，测试不受影响**。
- **注意**：若同批删掉某 CSS 规则（如 2.6 的 `.loop-desc`），`check-orphan-css.js` 会提示孤儿规则
  （警告级、不置红），顺手清掉即可。

#### 4.A.5 循环本段行精简（2.6）
- **做法**：开关关 → 隐藏「第 X 到 X 小节」+「只反复磨这几小节」整段；开 → 单行紧凑
  「循环本段 [开关] 第 X 到 X 小节」+ 删注脚；「循环本段」与上方「节奏型预设库」标题左缘对齐。
- **复核确认（见 §7）**：该面板只在**单一节奏型（预设）模式**出现；**曲式模式下整面板本就隐藏**，
  改它**不影响自定义曲式的播放/循环**。且下拉在开关关闭时**本就 `disabled`**，
  所谓"选区间即开循环"入口在关闭态本就不可达 ⇒ 关时隐藏**零功能损失**。
- **Ⅰ级注意（对既定设计的更改）**：`syncLoopUI` 里有一条注释明确写着"关着时灰掉而不是藏起来（位置稳定）"。
  本项反其道（关时隐藏），**属对既定设计决策的更改，必须同步改那条注释**，避免留下自相矛盾的说明。
- **待定细节**：底部 `loopHint`（"正在循环整个节奏型（N 小节）"/"共 Z 小节"）与行内范围文案重叠，
  精简后是否合并/保留需在批内定夺（建议保留"共 Z 小节"信息）。
- **测试**：动工前先 `grep` 复核现有对 `loopToggle|loopPanel|循环本段` 的断言后再改；新增
  `t137-loop-panel-compact`。

#### 4.E.2 内置型 1 小节 + 迁移（2.5）

- **复核确认（见 §7）**：静音拍按"线性小节 % N"判，与型小节数无关 ⇒ 无影响；循环区间在 1 小节型下
  选项退化但音乐无损失（内置型本就是同一小节复制）。**真正影响只有一处：已存曲式会变短**
  （曲式块存引用 + 遍数，段长 = 遍数 × 型的当前小节数），故迁移后长度逐小节不变。
- 测试：迁移矩阵加「v2.73 曲式块 ×4」行；涉及小节数的断言同步；
  **反向验证**：迁移前 8 小节 → 迁移后仍 8 小节。

## 8. 附录 · 两个思考题的结论（承前分析）

- **① 是否进 3.0？** 否。本批全是**增量功能 + 交互优化**，数据层仅纯增量字段（静音拍参数、段标注均带默认值，
  老存档零迁移），无破坏性变更，不构成 major。且 push 即触发线上部署，一批十几个改动合一个版本回归面太大；
  拆 6 批后各自可独立回滚。**值得升 3.0 的时机**：出现数据格式不兼容变更，或启动 §② 的架构变革。
- **② 单文件零依赖是否限制体验与开发？** 是有限制，但利大于弊，**现在不改**。该约束本身是产品价值
  （双击即用、`file://` 直开）。真实痛点是单文件内导航成本、diff 巨大、无法代码分割。将来若要破，
  正确姿势是「`src/` 分模块 + 构建拼回单文件」——**运行时产物逐字节保持单文件零依赖**，红线不破。
  再评估阈值：多人并行协作冲突常态化 / 文件体量再显著增长 / 需要 i18n、主题包等天然多文件的特性。
